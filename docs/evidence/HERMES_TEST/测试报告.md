## 5. 缺陷清单

### BUG-1（严重，已修复）information_schema 列名大小写导致核心功能 500
- 现象：MySQL 8.4 下 `information_schema.columns` 查询返回的列标签是**大写**（TABLE_NAME/DATA_TYPE），pymysql DictCursor 的键因此为大写，而代码用小写键取值 → `KeyError: 'data_type'`。影响：创建规则（页面表单 + Agent 工具）、/api/schema、/api/health 全部失效。
- 证据：首次运行 pytest 3 failed / 1 passed；`quality.py:74` KeyError。
- 根因：TEST_RECORD 自述“本环境没有运行中的 MySQL 服务…未运行”，README 声称支持 MySQL 8.0+ 但从未在 8.x 上跑过（MySQL 8 起 information_schema 列名大写；MariaDB/老版本返回小写，掩盖了问题）。
- 修复：`app/quality.py` 增加 `_norm()` 将 fetch 行键统一转小写，`describe_schema`、`_validate_target` 两处应用。修复后 pytest **4/4 通过**，全链路实测正常。
- 建议：把 pytest 接入 CI，在真实 MySQL 8.x 上跑，而不是仅静态检查。

### OBS-1（低）无任何鉴权
- README 已声明“没有用户登录、权限隔离”，符合演示定位；但任何人能访问端口即可建规则/看数据。若部署到共享网络必须加认证。

### OBS-2（低）允许重复规则
- 同表+同字段+同参数可以重复创建（本次实测规则 #8 与 #10 完全重复，模型已主动提示）。业务上是否允许由需求决定，建议至少给重复提示。

### OBS-3（低）ENUM 允许值 255 字符上限与样例主键
- `allowed_values` 每项限 255 字符；`order_id` 被禁止作为校验字段（有明确报错文案，属于设计约束，非缺陷）。

## 7. 测试优先级 Top 5 与后续测试计划草案

结合本 App 的架构特点（统计准确性 > Agent 编排 > 持久化 > UI），建议优先级：

| 优先级 | 模块 | 理由 | 重点用例 |
| --- | --- | --- | --- |
| P0 | 规则执行统计引擎（quality.py 聚合 SQL） | 交付核心，一处错误全盘皆错 | 五计数口径、通过率舍入、ENUM 字节精确比较、NULL/空串/纯空格三分、快照不可变 |
| P0 | 规则创建校验（白名单+参数） | 防误用防注入的边界 | 非法表/字段/类型/参数、重复允许值、order_id、字符串类型限制 |
| P1 | Agent 工具编排（Deep Agents 链路） | 主要体验载体，模型行为不可控 | 组合任务、信息缺失追问、不猜值、“刚才”解析、工具失败时的诚实汇报 |
| P1 | 持久化与会话（runs 快照/chat_messages/重启恢复） | 历史回查是产品卖点 | 快照与实时数据隔离、进程重启恢复、RUNNING 悬挂清理 |
| P2 | Web 页面交互 | 交付面 | 表单白名单联动、弹窗统计展示、轨迹按钮、状态灯、降级文案 |

计划草案（分三轮）：
1. 第一轮（已完成）冒烟 + 验收场景 12 项 → 本次报告。
2. 第二轮：数据变化专项（插 25+ 异常行验证样例 20 条上限与全量统计）、并发运行同一规则（验证 RUNNING/执行独立性）、MySQL 断连演练（验证 503 与 FAILED 记录）、模型 API 超时/返回垃圾的容错。
3. 第三轮：性能（100 万行演示表的运行耗时）、安全（端口暴露风险、CORS、输入注入回归）、可移植性（Python 3.11/3.12 复测、MariaDB 兼容性）。
